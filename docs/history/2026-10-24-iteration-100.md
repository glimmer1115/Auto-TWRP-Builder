# 100회차 빌드 스크립트 수정 및 검증 기록

- 날짜: 2026-10-24
- 대상: SM-T583 (Exynos 7870, `gtaxladwifikx`)
- 기준 기록: [99회차 플래싱 결과 및 로그 분석](2026-10-24-iteration-99.md)

## 99회차 증거 요약

- 99회차 기록 당시 추출한 RECOVERY 파티션은 보관된 순정 recovery 이미지와 일치했고, `last_recovery`에는 TWRP 식별 표식이 없습니다. 다만 이는 다른 부팅 구간에서 TWRP가 실행되지 않았다는 뜻은 아닙니다.
- 로컬 로그의 크기와 SHA-256을 재대조했으며 99회차 기록에 적힌 값과 모두 일치합니다. `artifacts/iteration-99/Image`의 SHA-256도 `artifacts/iteration-97/Image`와 같습니다.

## 99회차 로그 재대조

- `last_last_kernel`의 별도 부팅 구간에는 PID 2524의 `recovery` 프로세스, `/init.recovery.samsungexynos7870.rc` 실행, `/sbin/usbwait.sh` 시작 기록이 있습니다. `twrp.crash_counter`, `ro.twrp.boot`, `ro.twrp.version` 속성 쓰기가 recovery 도메인에서 거부됐고 로그에 `permissive=0`으로 남았습니다. 이 흔적은 TWRP recovery가 해당 pstore 부팅 구간에서 실행됐음을 뒷받침합니다.
- 같은 구간의 커널 로그는 약 4.33초와 4.35초, 6.26초에 밝기 120을 기록합니다. 이는 해당 로그에 기록된 고속 반복 밝기 변경 증거가 없다는 뜻일 뿐, 사용자가 본 약 1초 화면 현상의 원인을 확정하지는 않습니다.
- `last_avc_msg_recovery`에서는 recovery 도메인이 `sysfs_android_usb`를 탐색하려다 거부된 항목을 확인했습니다. 이는 USB 초기화 실패의 유력한 진단 단서지만, 실기기 연결 상태나 adbd 열거 완료를 증명하지는 않습니다.
- pstore의 다른 구간에는 약 34.9초의 `Fatal exception in interrupt`, `hard_reset_hook_callback`, SMC lockup reason `0x1`이 있습니다. pstore가 여러 부팅 기록을 포함하고 있어 이 panic을 TWRP 화면 증상 또는 특정 이미지의 원인으로 단정할 수 없습니다.
- 정정 결론: 캡처된 pstore에는 TWRP recovery 실행 흔적이 있지만, 그 실행을 99회차 산출물의 해시와 연결할 자료는 없습니다. 별도 파티션 추출본은 순정 이미지와 일치하며 `last_recovery`는 삼성 recovery 로그입니다. 두 사실은 서로 다른 시점/부팅 기록일 수 있으므로 구분해서 보존합니다.

## 이번 회차 수정

- `scripts/build.py`에서 필수 입력/출력 인수를 argparse로 검증하고, 입력 이미지가 실제 파일인지 확인합니다.
- 생성한 `Android.bp`를 `-o`에 전달된 출력 경로 기준으로 찾도록 수정했습니다. 이전에는 출력 디렉터리의 basename을 현재 작업 디렉터리에 다시 붙여, 절대 경로 또는 다른 작업 디렉터리에서 실행하면 파일 탐색이 실패할 수 있었습니다.
- `Android.bp` 누락과 비정상 장치명은 명확한 오류로 중단합니다.
- `GITHUB_OUTPUT`을 덮어쓰지 않고 UTF-8 append 모드로 기록합니다. `DEVICE_PATH`는 실제 출력 경로를 사용합니다.

## 업로드 및 기기 상태

- 사용자는 대상 기기가 순정 삼성 펌웨어 기반 루팅 상태라고 알렸습니다. 이 문서는 사용자 제공 상태이며 여기서 기기에 접속해 독립 확인한 결과는 아닙니다.
- 사용자는 대상 기기가 순정 삼성 펌웨어 기반 루팅 상태라고 알렸습니다. 이 문서는 사용자 제공 상태이며 여기서 기기에 접속해 독립 확인한 결과는 아닙니다.
- 코드와 100회차 기록은 SSH를 통해 `origin/master`에 업로드했습니다. 커밋은 `08e2114`입니다. SSH 인증은 로컬 Git 푸시에서 사용했고 성공했습니다.
- recovery 이미지 또는 Actions artifact는 업로드하지 않았습니다. 현재 workflow는 Actions artifact 업로드를 사용하며, manifest 인증이나 artifact 배포 경로를 SSH 방식으로 변경하지 않았습니다.
- 100회차 TWRP 플래싱 후 로그는 제공되지 않았습니다. 따라서 새 플래싱 결과 분석과 후속 기기 수정은 미실시이며, 성공/실패 판정도 보류합니다.

## 다음 확인 항목

1. 실제 workflow 실행에서 generated tree 경로와 recovery 산출물 검증이 통과하는지 확인합니다.
2. Actions artifact의 recovery 이미지 SHA-256을 기록하고, Odin 대상이 RECOVERY인지 및 플래시 성공 여부를 별도로 확인합니다.
3. 자동 재부팅을 끄고 recovery로 직접 진입한 뒤 TWRP 식별 로그와 `/cache/recovery/sm-stage`를 수집해 빌드 산출물 해시와 함께 보존합니다.
4. SELinux의 TWRP 속성 set 거부와 `sysfs_android_usb` 탐색 거부를 해당 산출물의 정책/도메인 설정과 대조합니다. 근거 없이 permissive 범위를 넓히지 않습니다.
5. recovery ADB, 패널 밝기 및 pstore panic은 서로 다른 관찰값으로 분리하고, 새 로그의 근거가 확인된 항목만 수정합니다.
