# 100회차 빌드 스크립트 수정 및 검증 기록

- 날짜: 2026-10-24
- 대상: SM-T583 (Exynos 7870, `gtaxladwifikx`)
- 기준 기록: [99회차 플래싱 결과 및 로그 분석](2026-10-24-iteration-99.md)

## 99회차 증거 요약

- 추가 사용자 보고: 99회차 TWRP 플래싱 후 백라이트가 계속 켜져 있었고 recovery `adbd` 연결은 되지 않았습니다. 이후 순정 펌웨어로 복원했고, 루팅 및 기기 연결을 확인한 상태에서 커널과 로그를 추출했습니다.
- 현재 RECOVERY 파티션 추출본은 순정 recovery 이미지와 일치하고 `last_recovery`에도 TWRP 표식이 없습니다. 이는 테스트 후 순정으로 복원했다는 사용자 보고와 양립합니다. pstore에는 별도 부팅 구간의 TWRP 실행 흔적이 있습니다.
- 로컬 로그의 크기와 SHA-256을 재대조했으며 99회차 기록에 적힌 값과 모두 일치합니다. `artifacts/iteration-99/Image`의 SHA-256도 `artifacts/iteration-97/Image`와 같습니다.

## 99회차 로그 재대조

- `last_last_kernel`에는 PID 2524의 `recovery` 프로세스, `/init.recovery.samsungexynos7870.rc` 및 `/sbin/usbwait.sh` 실행 흔적이 있습니다. 사용자는 이 시험을 99회차 플래싱 결과로 보고했습니다. 다만 플래시 입력 이미지의 SHA-256이 보존되지 않아 특정 Actions 산출물까지 암호학적으로 연결되지는 않습니다.
- `adbd` 서비스 시작 및 `/dev/socket/adbd` 생성 기록이 있지만, 같은 구간의 kernel integrity audit는 `/sbin/adbd`의 `appraise_data`를 `bad-fs`, `bprm-check`를 `reset-integrity`로 거부합니다. 이어 Android USB gadget이 `already disabled`로 기록됩니다. 따라서 단순한 PC 드라이버나 대기 시간 문제로 좁히지 말고, adbd 실행 거부와 gadget bind 실패를 순서대로 확인해야 합니다.
- 같은 구간의 커널 로그는 약 4.33초와 4.35초, 6.26초에 밝기 120을 기록합니다. 이는 해당 로그에 기록된 고속 반복 밝기 변경 증거가 없다는 뜻일 뿐, 사용자가 본 약 1초 화면 현상의 원인을 확정하지는 않습니다.
- `last_avc_msg_recovery`에는 recovery 도메인의 `sysfs_android_usb` 탐색 거부와 `/sbin/adbd` integrity appraisal 거부가 있습니다. 현재 로그만으로 integrity 검사의 설정 주체나 우회 가능 여부를 확정하지 않으며, 이를 비활성화하는 변경은 적용하지 않습니다.
- pstore의 다른 구간에는 약 34.9초의 `Fatal exception in interrupt`, `hard_reset_hook_callback`, SMC lockup reason `0x1`이 있습니다. pstore가 여러 부팅 기록을 포함하고 있어 이 panic을 TWRP 화면 증상 또는 특정 이미지의 원인으로 단정할 수 없습니다.
- 밝기 로그의 120 기록은 부팅 구간에서 몇 초 간격으로 관찰됩니다. 이는 사용자 보고인 “백라이트가 계속 켜짐”을 반박하지 않으며, 밝기 120이 실제 광량이나 지속 점등 원인이라는 뜻도 아닙니다.
- 결론: 사용자는 99회차 플래싱 뒤 지속 점등과 recovery ADB 미연결을 보고했고, 테스트 후 순정 루팅 상태로 복원했습니다. pstore는 TWRP 실행을 뒷받침하지만 정확한 플래시 이미지 해시는 미확인입니다. 삼성 `last_recovery`, 복원 후 RECOVERY 파티션 해시, TWRP 구간이 포함된 pstore를 서로 다른 시점의 증거로 구분합니다.

## 이번 회차 수정

- `scripts/build.py`에서 필수 입력/출력 인수를 argparse로 검증하고, 입력 이미지가 실제 파일인지 확인합니다.
- 생성한 `Android.bp`를 `-o`에 전달된 출력 경로 기준으로 찾도록 수정했습니다. 이전에는 출력 디렉터리의 basename을 현재 작업 디렉터리에 다시 붙여, 절대 경로 또는 다른 작업 디렉터리에서 실행하면 파일 탐색이 실패할 수 있었습니다.
- `Android.bp` 누락과 비정상 장치명은 명확한 오류로 중단합니다.
- `GITHUB_OUTPUT`을 덮어쓰지 않고 UTF-8 append 모드로 기록합니다. `DEVICE_PATH`는 실제 출력 경로를 사용합니다.

## 검증

- VS Code 진단: 오류 없음.
- 가짜 `DeviceTree`를 이용한 실행 검사: 절대 출력 경로에서 `Android.bp` 생성/탐색, 정확한 `DEVICE_PATH` 출력, 기존 `GITHUB_OUTPUT` 내용 보존을 확인했습니다.
- 검증 결과: 통과. 실제 TWRP 소스 동기화, 전체 recovery 빌드, Actions 실행은 하지 않았습니다.

## 업로드 및 기기 상태

- 사용자는 대상 기기가 순정 삼성 펌웨어 기반 루팅 상태라고 알렸습니다. 이 문서는 사용자 제공 상태이며 여기서 기기에 접속해 독립 확인한 결과는 아닙니다.
- 추가 보고로 테스트 후 순정 복원, 루팅 상태 및 PC 연결이 완료됐습니다. 이 세션에서는 기기에 직접 접속해 재검증하지 않았습니다.
- 코드와 100회차 기록은 SSH를 통해 `origin/master`에 업로드했습니다. 커밋은 `08e2114`입니다. SSH 인증은 로컬 Git 푸시에서 사용했고 성공했습니다.
- recovery 이미지 또는 Actions artifact는 업로드하지 않았습니다. 현재 workflow는 Actions artifact 업로드를 사용하며, manifest 인증이나 artifact 배포 경로를 SSH 방식으로 변경하지 않았습니다.
- 100회차 TWRP 플래싱 후 로그는 제공되지 않았습니다. 따라서 새 플래싱 결과 분석과 후속 기기 수정은 미실시이며, 성공/실패 판정도 보류합니다.
- 이 세션에서 분석한 실기기 자료는 사용자가 보고한 99회차 시험 및 그 뒤 순정 복원 상태에서 추출한 로그입니다. 100회차 신규 빌드/플래시와 그 후속 로그 수집은 수행하지 않았습니다.

## 101회차 수정·검증 계획

1. Actions 산출물 파일명과 SHA-256을 플래시 전에 기록하고, 실제 선택한 Odin 파일, RECOVERY 대상, PASS 결과를 시험 기록에 함께 남깁니다. 플래시된 이미지와 산출물 hash를 먼저 연결합니다.
2. 백라이트 지속 점등은 현 상태에서 재현되는지, 화면은 켜져 있으나 영상만 멈춘 것인지 구분해 기록합니다. UNBLANK, 밝기 sysfs, 패널 `displayon` 및 stage 로그의 시간을 정렬하고, 관측 전에 밝기 코드나 timeout을 변경하지 않습니다.
3. ADB는 `adbd` 실행 → integrity appraisal 결과 → FunctionFS descriptor/endpoint 생성 → legacy gadget enable/bind → PC USB 열거 순으로 확인합니다. 특히 `/sbin/adbd`의 `bad-fs`/`reset-integrity` 원인과 생성된 바이너리/파일 메타데이터를 조사합니다. 원인 없이 SELinux 완화나 integrity 기능 해제를 추가하지 않습니다.
4. `permissive.te`와 `mark_permissive.py`의 의도한 정책 비트가 실제 플래시 이미지 `/sepolicy`에 들어갔는지 확인합니다. 현재 AVC의 `permissive=0`과 맞지 않으므로 산출물 provenance 및 policy 적용 여부를 확인하기 전 정책 변경은 보류합니다.
5. SM-T580/SM-T585 자료는 기기 트리·패널·커널 동작 비교를 위한 참조만 합니다. 해당 모델 recovery 이미지나 패키지를 SM-T583에 플래시하지 않습니다. 현재 SM-T583 전용 트리를 기본 경로로 유지하고, 검증된 SM-T583 전용 소스/maintainer가 발견될 때만 대안으로 평가합니다.
6. recovery ADB 확인과 Android의 rooted ADB 확인을 분리해 기록하고, 테스트 후 정상 부팅 및 순정 복원 경로도 확인합니다. panic은 별도 부팅 구간의 증거로 유지합니다.

## 새 세션 인계 메모

다음 세션은 101회차로 진행합니다. 99회차 시험 후 보고된 결과는 백라이트 지속 점등, recovery ADB 미연결입니다. 기기는 순정 펌웨어로 복원됐고 루팅 상태에서 PC 연결 및 로그 추출이 완료됐습니다. `artifacts/iteration-99/` 증거와 이 문서의 99회차 로그 재대조를 먼저 확인하세요. 우선순위는 플래시 산출물 SHA-256 고정, `/sbin/adbd`의 `bad-fs`/`reset-integrity` 거부 분석, USB gadget bind 단계 확인입니다. T580/585는 참조용이며 해당 이미지를 SM-T583에 플래시하지 마세요. 새 로그가 없는 상태에서 백라이트 코드, 대기 시간, SELinux/integrity 정책을 추가 변경하지 마세요.

각 workflow/실기기 세션 종료 시 이번 회차의 입력 이미지와 산출물 SHA-256, Odin 대상/PASS, Android와 recovery ADB를 각각 기록하고, 다음 회차 번호·미확인 항목·금지할 가정을 이 인계 메모에 갱신합니다.
