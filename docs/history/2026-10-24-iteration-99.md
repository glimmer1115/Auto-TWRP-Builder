# 99회차 플래싱 결과 및 로그 분석

- 날짜: 2026-10-24
- 대상: SM-T583 (Exynos 7870, `gtaxladwifikx`)
- 빌드 기준: ARM32 recovery (`armeabi-v7a`, `init` ELF32), 순정 kernel Image 별도 사용
- 이번 세션 반영 커밋: `99476ae` (`fix: enforce ARM32 recovery kernel checks`)

## 실기기 결과

- 사용자 보고: 최초 화면에서 화면 전체 백라이트가 약 1초간 강하게 점등된 뒤 이전과 같은 지속 현상이 남음.
- 재부팅 후 Android 8.0에서 root ADB 연결을 확인함. 이는 Android ADB 연결 확인이며 recovery ADB 연결 성공을 뜻하지 않음.
- 현재 `RECOVERY` 파티션(`/dev/block/mmcblk0p11`)을 읽기 전용 추출함. 크기 39,845,888바이트, SHA-256 `4cfed1508346022a45dbc479aa657aeffad67d5ab5f68450d60eada4f6ced36d`.
- 추출 이미지가 로컬 `artifacts/iteration-97/recovery.img`와 바이트 단위로 동일함. 따라서 현재 파티션에서 99회차 TWRP 이미지가 확인되지 않으며, 보고된 플래시 결과가 새 빌드 이미지에서 나온 것인지 아직 확정할 수 없음.

## 커널 및 로그

- 현재 recovery 이미지에서 추출한 kernel은 16,989,448바이트 ARM64 `Image`이며 헤더 매직은 `ARMd`임. SHA-256 `bb2b9eb31c003f2f6d71648ec738988caaf58c2aabb642dcbc8fe1e23a7e57bc`.
- 커널은 이전 보관본 `artifacts/iteration-97/Image`와 일치함. 이는 recovery 사용자 공간을 64비트로 설정해야 한다는 뜻이 아님.
- `last_recovery`에는 `TWRP`, `Team Win`, `SM-T583 stage`, `sm-stage` 표식이 없고, Samsung recovery 기록에서 약 12.1초 시점에 정상 reboot 절차가 시작됨.
- 화면 초기화 로그: `/sys/class/leds/lcd-backlight/brightness` 접근 실패 후 DRM sysfs 경로를 사용함. 최대 밝기 읽기도 실패함. DECON UNBLANK는 약 5.44초, 패널 `displayon`은 약 5.61초, 밝기 128 기록은 약 5.66초와 5.68초에 확인됨. 약 1초간의 광량 변화 자체를 입증하는 반복 밝기 쓰기나 원인은 로그에서 확인되지 않음.
- USB 로그에는 Android USB gadget 준비 기록이 있으나 FunctionFS 활성화 시점에 `android_usb: already disabled`가 있음. `last_avc_msg_recovery`에는 init의 `/dev/usb-ffs/adb` mounton 및 recovery 도메인의 `sysfs_android_usb` 탐색 거부가 포함됨. 이 로그는 TWRP 마커가 없는 recovery 기록이므로 새 TWRP의 ADB 실패로 단정하지 않음.
- pstore 전체 버퍼 `last_last_kernel`에는 한 부팅 구간에서 약 34.98초의 `Kernel panic - not syncing: Fatal exception in interrupt`, `hard_reset_hook_callback`, SMC lockup reason `0x1`이 기록됨. 여러 부팅 구간이 이어진 버퍼라 99회차 TWRP 이미지와의 직접 연관은 미확정이며, 화면 깜박임 원인으로 연결하지 않음.

## 이번 세션의 빌드 변경

- recovery ABI는 ARM32 `armeabi-v7a`로 명시하고 기존 ELF32 `init` 검사를 유지함. 이전 64비트 recovery 설정에서 같은 실패가 반복됐다는 사용자 확인을 반영해 64비트 recovery는 후보에서 제외함.
- workflow의 커널 추출 단계는 입력 크기와 Exynos 7870 순정 ARM64 Image 헤더를 검사하고 SHA-256을 출력함. 이는 순정 커널 입력 검증이며 recovery ABI를 64비트로 바꾸지 않음.
- Python heredoc 진단 문자열은 Windows 인코딩에 영향받지 않도록 ASCII 영어로 변경함.

## 다음 조치

1. 다음 시험 전에 Odin에 넣은 99회차 산출물의 파일명과 SHA-256을 기록하고, Odin의 대상이 RECOVERY였으며 기록이 PASS였는지 확인함.
2. Samsung 순정 recovery가 실행되거나 복원되는 경로를 배제하도록 Auto Reboot를 끄고 플래시 직후 recovery로 직접 진입하는 절차로 재확인함. Android 부팅 후에는 RECOVERY 파티션 해시를 다시 읽어 새 이미지가 실제 기록됐는지 확인함.
3. 실제 99회차 이미지가 기록된 상태에서 TWRP 고유 로그 및 `/cache/recovery/sm-stage`를 확보한 뒤에만 패널/백라이트와 recovery USB 변경을 평가함.
4. TWRP 로그가 확보되면 최초 패널 UNBLANK 이후의 brightness/sysfs 쓰기를 대조하고, USB는 FunctionFS mount 및 `sysfs_android_usb` AVC 거부의 주체·시점·도메인을 확인함. 근거 없이 대기 시간을 늘리거나 광량 코드를 더 바꾸지 않음.
5. Android ADB 연결과 recovery ADB 연결 결과를 별도 항목으로 계속 기록함.

## 확인 상태

99회차 플래싱 후 사용자가 보고한 증상은 기록했으나, 현재 파티션·로그는 순정 Samsung recovery와 일치함. 새 TWRP 이미지가 실제로 부팅된 증거를 확보하기 전까지 이번 화면 결과를 99회차 TWRP 변경의 회귀/성공 판정으로 사용하지 않음.
